# Implementation decisions

These decisions were recorded during implementation and the single final review fix pass. No Minor review findings were deferred.

- Use existing isolated worktree on fix/review-completion from 838f762; keep main and global Java/Maven configuration untouched — user requires no impact on other repos — cost if wrong: changes require a later integration step into main.
- Honor the user's detailed follow-up as the approved design and execution order; create a concise plan and implement without another approval round — developer instructions preserve task authorization — cost if wrong: implementation choices are reviewable in the new supplement/plan.
- Record the actual clean verify once per user stage rather than repeating the identical suite solely via task-done — latest developer instructions prohibit unjustified repeated testing — cost if wrong: the ledger completion is written manually from observed command output.
- Opening/closing boundaries that are nonexistent or ambiguous under DST are rejected, rather than silently shifted — protects declared hours; UTC request instants and elapsed durations across DST are supported — cost if wrong: a dealership intentionally using an ambiguous boundary needs an explicit offset policy later.
- Relay claims one row per short transaction and drains at most ten rows per scheduled invocation; Kafka sends have bounded timeouts, and stale completion is fenced by a UUID claim token — prevents waiting messages exhausting leases — cost if wrong: lower throughput than large parallel batches; duplicate delivery still requires durable consumer deduplication in a real downstream service.
- Kafka advertised host listener uses localhost:29092, internal listener kafka:19092; exact user-specified images were verified available — avoids using another project's common broker port — cost if wrong: clients must use the documented non-default host port.
- Cache entries are validated for requested ID and required metadata fields before use; exceptions and invalid values fall back to DB, with 100 ms connect/command timeouts — prevents corrupt Redis data causing booking errors — cost if wrong: slow-but-healthy Redis can be bypassed more often; TTL can retain catalog changes for up to one hour as requested.
- Health/readiness requires Postgres, while Redis and Kafka are optional for booking and excluded from aggregate health; future metrics should surface outbox backlog independently — preserves fail-open availability — cost if wrong: UP alone does not prove the broker/cache is healthy, so Kafka UI/outbox state remains part of the demo.
- Native server binds 127.0.0.1 by default; Compose overrides the container bind address while publishing only localhost host ports — supports local-only development and container reachability — cost if wrong: remote native access requires explicit configuration.
- Retry topic provisioning on the relay thread before claiming rows; disable consumer auto-creation — booking/startup must tolerate broker absence and later restore three partitions — cost if wrong: topic reconciliation delays delivery while broker is unavailable; booking stays durable.
- Pause only the disposable Kafka test container rather than stop/start — retains its dynamically assigned host port and isolates the intended outage behavior — cost if wrong: this tests unresponsive startup rather than a physical broker restart; separate outage test covers stopped broker.
- Use localhost:18080 for the demo and stop only newly started app/Kafka/UI/Redis services afterward — preserve the existing 8080 process and PostgreSQL data — cost if wrong: demo needs an explicit port override and restart command.
- Idempotency, cancellation and availability endpoints remain Designed-only — explicitly outside approved implementation scope — cost if wrong: retrying clients and later cancellation need API/schema work.
- Overnight hours, holidays and technician shifts remain outside the daily opening-hours model — approved scope validates existing daily boundaries — cost if wrong: unsupported calendar scenarios require a richer model.
- Accept catalog staleness up to one hour and defer administration/invalidation — matches requested TTL and read-through scope — cost if wrong: catalog updates may not apply immediately.
- Defer durable consumer deduplication and future confirmed/cancelled ordering — current consumer logs only and delivery is explicitly at-least-once — cost if wrong: a future side-effecting consumer must implement both before production use.
- Manual replay tooling, backlog metrics and distributed tracing remain Designed-only — expose inspected outbox state and basic health/logs for this demo — cost if wrong: operators need manual SQL inspection and have less incident visibility.
- Production replication, authentication and TLS remain outside the localhost demo — requested Compose is a single-broker development stack — cost if wrong: this deployment must not be reused as production configuration.
- Malformed third-party Kafka payload handling remains outside the logging demo — scheduler emits a tested CloudEvent contract — cost if wrong: external producers require consumer validation and dead-letter handling.
- Complete the Compose smoke in the parent after review — pending runtime evidence is resolved by the final rebuilt image checks — cost if wrong: a local smoke does not prove every deployment environment.
- Integrate into main and push under the user's standing explicit instruction; retain the host-managed worktree — no renewed approval needed, exact tested source is fast-forwarded — cost if wrong: main changes immediately; no force push or global settings change is permitted.
